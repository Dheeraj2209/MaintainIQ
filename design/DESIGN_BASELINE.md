# Design Baseline

## Smart Predictive Maintenance Decision-Support System

This document is the single source of truth for project scope and design decisions. Where it conflicts with any other document in this repository (including `SRS_Document.md` or the diagrams), **this document wins**. It exists because the repo accumulated several rounds of design documents (project idea → feature expansion → SRS → PlantUML diagrams) that disagreed on scope in places. See `Technical_Presentation_Material.md`'s "Repository Analysis Summary" for the document history.

## Resolved scope decisions

| Topic | Decision | Why |
| --- | --- | --- |
| Hardware vs. dataset | Dataset-only pipeline first. Real ESP32 + sensor hardware is a later milestone, not a prerequisite. | The SRS already treats dataset-based demonstration as a valid, risk-mitigated path; none of the diagrams designed a dataset-input flow even though they assume live hardware. Building against a dataset lets the ML/pipeline work start immediately. |
| Machine scope | Multi-machine (factory-floor scenario) from the start. | Matches the diagrams (`multimachine_uml_class.puml`, `factory_scenario_description.puml`), which are the most concrete and recent design layer. Single-machine documents (`PROJECT_CONTEXT.md`, `Academic_Project_Presentation.md`) are superseded. |
| Temperature sensor | Mandatory for every machine, not optional. **Superseded (XJTU-SY spec):** temperature is not part of the canonical data model; it survives only in the quarantined legacy IMS pipeline. See `docs/superpowers/specs/2026-08-06-xjtu-sy-ml-integration-design.md`. | Matches `feature_requirements_to_include.md` and the UML class diagram, which model it as a required part of every sensor module. Simplifies the data model. |
| Root cause identification | A real module in the MVP, not deferred. Rule-based to start. | The SRS defines it as a first-class feature (FR-23–26), but no diagram gave it a distinct module — it was folded into vague "alert logic." It needs an actual design, not a placeholder. |
| Alert triggering | ML-model-driven once a model is trained and validated, with the rule-based classifier kept as an always-available fallback. **Refined by** the XJTU-SY spec (`2026-08-06-xjtu-sy-ml-integration-design`): alerts derive from RUL/health-state model output. | The rule-based classifier alone under-uses the SRS's own ML requirements (FR-18–22). ML models generally outperform fixed thresholds, but the SRS also flags "limited labeled fault data" as a risk — the rule-based path stays as a safety net when ML confidence is low or a model isn't deployed yet. |
| ML model selection | Train several candidate models on the same feature set and benchmark them; deploy whichever wins, plus keep an unsupervised anomaly detector as an option when fault labels are scarce. Candidates: Random Forest, Gradient Boosting (XGBoost/LightGBM), SVM, Logistic Regression (baseline), Isolation Forest (unsupervised anomaly detection). A raw-signal deep model (1D-CNN/LSTM) is noted as a future option if enough labeled data becomes available. **Refined by** `docs/superpowers/specs/2026-08-06-xjtu-sy-ml-integration-design.md`: the deployed model is the XJTU-SY RUL regressor; the classifier candidates below are historical. | The pipeline produces tabular feature vectors per window (RMS, peak, mean, std, optional FFT), which favors classical ML over deep learning for a small academic dataset. Isolation Forest specifically addresses the SRS's "limited labeled fault data" risk since it needs no fault labels. |
| Maintenance history | Manual entry via a dashboard form/API. | No diagram designed how maintenance records get into the system; SRS's KPIs depend on "last maintenance date" existing. Manual entry is the simplest way to close that gap for a prototype. |
| Backend/ML stack | Python + FastAPI. | The only concrete technology hint across all documents (`training_inference_upstream_downstream.puml` assumes a FastAPI-style inference service); Python fits every other document's ML/data-processing expectations. |
| Storage | SQLite. Schema is the XJTU-SY canonical model — see `docs/DATA_MODEL.md` and `2026-08-06-xjtu-sy-ml-integration-design`. | Matches the SRS's "lightweight database" option; no cloud dependency needed for an academic prototype. |
| Dashboard | Web dashboard. **React 19 + TypeScript + Vite + Tailwind CSS**, charts via `recharts`. Built to static assets (`frontend/dist`) and served by the FastAPI backend from the same origin (Vite dev proxy forwards `/api` during development). Supersedes the earlier vanilla-JS/Chart.js dashboard. | The vanilla-JS prototype met NFR-13 but was untestable and hard to extend. A typed component stack lets the UI be built test-first (Vitest + React Testing Library + MSW), keeps the API contract honest at compile time (`src/api/types.ts` mirrors the Pydantic schemas), and still ships as plain static files — no server-side rendering or extra runtime infrastructure. The build step is the only added dependency, justified by the testability gain. |
| Testing strategy | Frontend built test-driven (Vitest + React Testing Library + MSW mock server; red→green per component). Backend covered by a pytest suite (FastAPI `TestClient` + `dependency_overrides` against a temp SQLite DB) — added after the API stabilized, so honestly test-after, not TDD. No external secrets: the prototype is dataset-only (local SQLite); `frontend/.env.example` documents `VITE_API_BASE_URL` and reserves an M6 MQTT-broker-credentials placeholder (backend-side, never in the browser bundle). | The React layer is where regressions are cheapest to catch early and where TDD paid off; retrofitting identical rigor onto already-written backend code would have been theater. Documenting the split honestly (per this repo's "flag what isn't" convention) keeps the claim accurate. |
| KPI computability (SRS 7.4) | Compute the KPIs a dataset-only prototype can actually support; report the rest with an explicit `{"status": "not_applicable", "reason": ...}` marker instead of omitting them, so the KPI response contract is stable once live telemetry (M6) lands. **Computable now:** all Machine Health KPIs, all Maintenance KPIs, and the model-quality Prediction KPIs (accuracy, false alarms, missed faults, confidence from `models/evaluation_report.json`). **Partially computable:** root-cause accuracy (only the XJTU-SY dataset's documented run-to-failure bearing wear — matches `src/root_cause/rule_based.py`'s caveat) and Operational-Value KPIs (faults-detected-before-failure using XJTU-SY documented run-to-failure bearings; maintenance-priority score per machine). **Not applicable until M6:** all System-Performance KPIs (sensor collection rate, transmission success, edge buffer, cloud sync) and the longitudinal Operational KPIs (breakdown / emergency-maintenance reduction). | Continues this repo's "implement what's real, flag what isn't" convention (see `src/prediction/router.py`, `src/storage/db.py`). System-Performance KPIs describe live-hardware telemetry health that doesn't exist yet; breakdown/emergency-reduction KPIs need before/after real-world data, a limitation the SRS itself flags in Section 10. |
